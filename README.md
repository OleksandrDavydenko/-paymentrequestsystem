# Система заявок на оплату

Flask-додаток з входом через Microsoft Entra ID (лише користувачі нашої організації).

## Локальний запуск
```
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
copy .env.example .env   # заповнити значення
.venv\Scripts\python app.py
```
Відкрити http://localhost:5000

## Налаштування Azure
**App registration** (Entra ID → App registrations → Payment Request System):
- Supported account types: *My organization only* (single tenant)
- Authentication → Web → Redirect URIs:
  - `http://localhost:5000/getAToken`
  - `https://paymentrequestsystem-ece9b4b4g0dbe7fu.polandcentral-01.azurewebsites.net/getAToken`

**App Service** → Environment variables:
| Name | Value |
|---|---|
| CLIENT_ID | Application (client) ID |
| TENANT_ID | Directory (tenant) ID |
| CLIENT_SECRET | client secret |
| FLASK_SECRET_KEY | випадковий рядок |
| REDIRECT_URI | `https://paymentrequestsystem-ece9b4b4g0dbe7fu.polandcentral-01.azurewebsites.net/getAToken` |
| SCM_DO_BUILD_DURING_DEPLOYMENT | `true` |

Startup command: `gunicorn --bind=0.0.0.0 --timeout 600 app:app`

## Деплой
Кожен push у `main` деплоїться через GitHub Actions (`.github/workflows/deploy.yml`).
Потрібен секрет репозиторію `AZURE_WEBAPP_PUBLISH_PROFILE` — вміст publish profile з App Service
(App Service → Configuration → SCM Basic Auth Publishing = On → Overview → Download publish profile).

## Ролі та групи
Ролі = членство в групах безпеки Microsoft Entra ID. Адмінка (`/admin/users`) змінює членство через Microsoft Graph
від імені адміністратора, що увійшов.

| Роль | Група | Змінна App Service |
|---|---|---|
| Адміністратор | PRS Адміністратори | `GROUP_ADMIN` |
| Ініціатор | PRS Ініціатори | `GROUP_INITIATOR` |
| Бухгалтер (готівка) | PRS Бухгалтери — готівка | `GROUP_ACC_CASH` |
| Бухгалтер (безготівка, резидент) | PRS Бухгалтери — резиденти | `GROUP_ACC_RESIDENT` (стара назва `GROUP_ACCOUNTANT` теж працює) |
| Бухгалтер (безготівка, нерезидент) | PRS Бухгалтери — нерезиденти | `GROUP_ACC_NONRESIDENT` |
| Фіндиректор | PRS Фіндиректори | `GROUP_CFO` |

`ADMIN_EMAILS` (за замовчуванням `od@ftpua.com`) — завжди адміністратори, навіть без групи.

Налаштування в Entra ID:
- App registration → Token configuration → Add groups claim → Security groups (ID token: Group ID)
- API permissions → Microsoft Graph (Delegated): `User.ReadBasic.All`, `GroupMember.ReadWrite.All`,
  `GroupMember.Read.All` → Grant admin consent

Маршрут погодження: Ініціатор → Бухгалтер → Фіндиректор → Оплата. Режим задається в «Адмініструванні →
Налаштування процесу» (`data/app_settings.json`, на Azure — `/home/data/`):
- **послідовно** — фіндиректор отримує заявку після погодження бухгалтера;
- **паралельно** — заявка одразу в обох (статус «На погодженні»), до оплати — коли погодили обидва.
Режим запам'ятовується в заявці під час відправки: зміна діє на нові та повторно відправлені заявки.

Коментарі: кожен, хто бачить заявку, може залишити коментар на будь-якому етапі — статус не змінюється,
коментар потрапляє в історію.
Бухгалтер (і перевірка, і оплата) визначається формою оплати та організацією заявки:
- Готівка → бухгалтер готівки (для будь-якої організації);
- Безготівка + організація-резидент (напр. ФТП) → бухгалтер резидентів;
- Безготівка + організація-нерезидент (напр. Litbia) → бухгалтер нерезидентів.

Резидентність організації — з довідника 1С (країна Україна — резидент). Організації можна призначити іншого
бухгалтера: «Адміністрування → Організації → Готівка / Безготівка — хто перевіряє» (напр. ФОП, якого веде бухгалтер
готівки). Призначення діє одразу й на заявки в роботі; колонка «Форма оплати» у списках не змінюється.

### Відділи, керівник відділу, учасники заявки
Усі налаштування людини — в її **картці** («Адміністрування» → клік по людині або «+ Додати користувача» →
пошук в Azure → картка): ролі, відділ співробітника, які відділи очолює / заявки яких бачить, статті бюджету,
з поясненнями до кожного пункту й однією кнопкою «Зберегти» (`/admin/users/<id>`).

Окремі, незалежні налаштування:
- **Відділ співробітника** («Користувачі та ролі») — один відділ, до якого людина належить. Довідник відділів —
  окремий (`departments.py`, поки мокові дані; пізніше — запит з Power BI), не пов'язаний із відділами статей.
  Заявка запам'ятовує відділ автора під час створення.
- **Розділ «Відділи»** (`data/org_structure.json`, на Azure — `/home/data/`): у кожного відділу **один керівник**
  (одна людина може очолювати кілька відділів) і список тих, хто **бачить заявки відділу** (заступники, менеджери).
  Це не групи Azure: ролі «Керівник відділу» / «Перегляд заявок відділу» з'являються під час входу самі.
  Керівник і ті, хто бачить, мають розділ «Заявки відділу» (без чернеток) і можуть коментувати.
  Якщо керівника змінити — заявки, що чекають його погодження, переходять до нового.
- **Погодження керівником** — у «Налаштуваннях процесу»: «лише бачить» або «погоджує першим кроком»
  (далі послідовно або паралельно). Автор-керівник свого відділу — крок зараховується автоматично;
  без відділу чи без керівника — крок пропускається (запис в історії).
- **Учасники заявки** (як «копія» в листі): автор або адмін додає колег зі списку користувачів системи.
  Учасник бачить заявку (і чернетку), коментує, додає файли й отримує ті самі листи, що й автор
  («Вас додано до заявки…» — першим); редагує й відправляє заявку лише автор. Вкладка «Мої заявки → Я учасник».
- **Статті бюджету** — як і раніше, окремо для кожного користувача.

## Довідник статей витрат (Power BI)
Статті беруться з семантичної моделі Power BI, таблиця `Expense_Item` (`expense_items.py`).
Доступ — від імені додатку (service principal) з тими самими `CLIENT_ID` / `CLIENT_SECRET` / `TENANT_ID`.
Користувачу показуються лише елементи: групи (за `Тип_вузла` або наявністю дочірніх рядків) приховано.

| Змінна | Значення |
|---|---|
| `PBI_GROUP_ID` | ID workspace Power BI |
| `PBI_DATASET_ID` | ID семантичної моделі |
| `PBI_TABLE` | `Expense_Item` (за замовчуванням) |
| `PBI_CACHE_MINUTES` | як часто перечитувати довідник, за замовчуванням 60 |

Налаштування Power BI (одноразово):
- Admin portal → Tenant settings → «Service principals can use Fabric APIs» → Enabled
  (можна обмежити групою безпеки, до якої додано додаток);
- Admin portal → Tenant settings → «Dataset Execute Queries REST API» → Enabled;
- Workspace → Manage access → додати `Payment Request System` (Viewer; якщо не вистачить — Contributor).

Довідник оновлюється сам: раз на `PBI_CACHE_MINUTES` хвилин у фоні (користувач не чекає Power BI —
поки йде оновлення, показується попередній список). Після перезапуску одразу береться збережена копія.

Тип статті: без відділу — **пряма**, з відділом (колонка «Відділ») — **з розподілом**; одна стаття
може мати кілька відділів.

### Статті бюджету користувачів
В «Адмініструванні» для кожного користувача задається, які статті він може вибирати в заявці:
прямі статті, усі відділи або вибрані відділи. Без налаштувань — **жодної статті**.
Налаштування зберігаються у `/home/data/user_budget.json` (локально `data/`), ключ — Entra object id.

Без `PBI_GROUP_ID`/`PBI_DATASET_ID` працюють мокові статті. Остання вдала копія довідника
зберігається у `/home/data/expense_items.json`. Стан і кнопка «Оновити зараз» — в «Адмініструванні».

## Секрети
- Секрети (`CLIENT_SECRET`, `FLASK_SECRET_KEY`, publish profile) — **лише** в App Service → Environment variables,
  у секретах GitHub і в локальному `.env`. У коді немає значень за замовчуванням для секретів.
- `.env`, `*.PublishSettings`, `data/`, `*.csv` — у `.gitignore`. Скрипти з паролями в репозиторій не додаються.
- Паролі користувачів системі не потрібні: доступ до Power BI й Graph — через реєстрацію додатку.
- Якщо секрет потрапив у коміт, чат чи пошту — одразу замініть його (App registration → Certificates & secrets →
  New client secret, оновити `CLIENT_SECRET` в App Service і `.env`, видалити старий). Видалення з історії git
  не допомагає, якщо репозиторій уже був публічним.

## Email-сповіщення
Листи надсилаються через **SMTP** будь-якої пошти (Gmail / Google Workspace, Microsoft 365, SendPulse…).
Усе налаштовується в «Адмініструванні → Email-сповіщення»: сервер, порт, шифрування, логін, пароль додатку,
відправник; там же тестовий лист і журнал останніх листів. Пароль зберігається **зашифрованим**
(ключ виводиться з `FLASK_SECRET_KEY`; якщо його змінити — пароль треба ввести заново) і ніколи не показується.

Gmail / Google Workspace: smtp.gmail.com, 587, STARTTLS; на акаунті відправника — двоетапна перевірка
і «пароль додатку» (myaccount.google.com → Безпека → Паролі додатків).

Користувачі вибирають події в меню «✉ Сповіщення на пошту» (`data/user_prefs.json`, на Azure — `/home/data/`).
Щоб знати, кому з погоджувачів надсилати, сервер читає склад груп ролей через Microsoft Graph:
потрібен application-дозвіл `GroupMember.Read.All` з admin consent. Він дає лише ID учасників, тож пошту
система бере з довідника `user_directory.json` (заповнюється, коли людина входить у систему або коли адмін
відкриває «Адміністрування»); з дозволом `User.ReadBasic.All` (Application) пошта приходить одразу.

**Інша пошта.** Якщо адмін увімкнув «Дозволити користувачам вказувати іншу пошту», користувач може в
«Сповіщеннях на пошту» вказати будь-яку адресу. Вона **замінює** робочу лише після переходу за посиланням
з листа підтвердження (діє 48 год, потрібен вхід тим самим обліковим записом); до того листи йдуть на робочу.
Якщо параметр вимкнути — листи знову йдуть на робочу пошту, збережені адреси лишаються.

`APP_BASE_URL` (необов'язково) — адреса сайту для посилань у листах.

## Дані з 1С (через Power BI)
**Підключено:** `Expense_Item` (статті витрат), `Organizations` (організації: Code, Name, EDRPOU, Country,
CountryGUID, IsDeleted; ключ — Code; резидент — лише країна Україна, порожня чи інша країна — нерезидент) і
`Departments` (відділи співробітників: Код_відділу, Назва_відділу) і `Counterparties` (контрагенти: GUID, Code,
Name, FullName, Edrpou, IsNonResident, IsDeleted; ключ — GUID; DirectQuery). Контрагентів десятки тисяч, тому пошук
іде на сервері (`/counterparties/search`), кеш оновлюється раз на 15 хв (`PBI_COUNTERPARTIES_MINUTES`). Новий
контрагент, ще не заведений у 1С, перевіряється наживо за ЄДРПОУ (DAX-запит) кнопкою «Перевірити в 1С зараз» і
автоматично перед «Оплачено». Новий контрагент: назва обов'язкова; для резидента — ЄДРПОУ 8 цифр (юрособи) або
10 цифр (ІПН ФОП / фізосіб) з перевіркою контрольної цифри (код, що вже є в 1С, пропонується як наявний);
для нерезидента номер необов'язковий. Той самий датасет (`PBI_GROUP_ID`,
`PBI_DATASET_ID`); назви таблиць можна змінити змінними `PBI_ORGANIZATIONS_TABLE`, `PBI_DEPARTMENTS_TABLE`.
Кеш — у пам'яті й файлах `pbi_*.json` (`/home/data/`), оновлення — раз на `PBI_CACHE_MINUTES` у фоні або
кнопкою «⟳ Оновити зараз» в адмінці. Помічені на видалення не пропонуються для вибору, але старі заявки їх показують.
«Вид оплати» обов'язковий, лише якщо для організації заявки в довіднику є рахунки / каси.

Довідники приходять з 1С через таблиці датасету Power BI (той самий сервісний принципал і `executeQueries`, що й
для статей витрат). Поки таблиці не підключені — мокові дані у тому ж форматі. Для кожної таблиці: ключ —
GUID посилання 1С, позначка видалення, дата зміни (якщо є), лише елементи (без груп).

| Таблиця | Колонки | Для чого |
|---|---|---|
| Counterparties ✔ | GUID, Code, Name, FullName, Edrpou, IsNonResident, IsDeleted | вибір контрагента, дублі, автоприв'язка нових |
| Contracts | GUID, GUID контрагента, GUID організації, Номер, Дата, Назва, Валюта, Вид, Позначка видалення | договір у заявці |
| Organizations | GUID, Код, Назва, ЄДРПОУ, Країна/Резидент, Позначка видалення | «Організація», бухгалтер резидент/нерезидент |
| OrganizationAccounts | GUID, GUID організації, Назва, IBAN, Банк, Валюта, Основний, Позначка видалення | «Вид оплати» (безготівка) |
| CashDesks | GUID, GUID організації, Назва, Валюта, Позначка видалення | «Вид оплати» (готівка) |
| Invoices | GUID, Номер, Дата, GUID організації/контрагента/договору, Сума, Валюта, Залишок до оплати, Призначення | «Підбір рахунків» |
| Expense_Item | + GUID, Позначка видалення | статті витрат |
| Departments | GUID, Код, Назва, Батько, Закритий | відділ співробітника |
| Employees (за бажанням) | GUID, ПІБ, Робоча пошта, GUID відділу, Посада, Звільнений | відділ за поштою входу |
| Payments (на майбутнє) | GUID, Дата, Сума, Валюта, GUID контрагента, Номер заявки | автоматична позначка «Оплачено» |

**Види оплати.** `PaymentTypes` (GUID, Code, Name, IsDeleted) і `UserPaymentTypes` (UserGUID, UserName,
PaymentTypeGUID, IsDeleted — вкладка «Виды оплаты» картки користувача 1С). У полі «Вид оплати» бухгалтер бачить лише
свої види оплати з 1С, фіндиректор — усі. Користувача системи зв'язують з користувачем 1С у картці користувача
(«5. Користувач 1С»; система підказує найсхожішого за іменем; файл `data/user_onec.json`). Без зв'язку або без видів
оплати поле необов'язкове.

**Новий контрагент, якого ще немає в 1С.** Ініціатор вносить його у вікні вибору контрагента («+ Новий
контрагент»: ЄДРПОУ / реєстр. номер, назва, коментар; перевірка дублів за ЄДРПОУ). Бухгалтер заводить його в 1С
і прив'язує в картці заявки (або система прив'язує сама за ЄДРПОУ під час оновлення довідників). Параметр
«Контрагент, якого ще немає в 1С» у «Налаштуваннях процесу»: заборонити «Оплачено» до прив'язки (за замовчуванням)
або дозволити з попередженням. Тимчасові контрагенти — `data/counterparties_pending.json` (на Azure — `/home/data/`).

**Вид оплати** — рахунок (безготівка) або каса (готівка) організації, з якої платимо. Бачать і змінюють лише
бухгалтери й фіндиректор; обов'язковий для погодження бухгалтером і для оплати; ініціатор поля не бачить
(ні в картці, ні в історії, ні в листах).
