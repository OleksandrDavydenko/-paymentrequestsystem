# PayDesk — система заявок на оплату

Flask-додаток з входом через Microsoft Entra ID (лише користувачі нашої організації).

## Локальний запуск
```
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
copy .env.example .env   # заповнити значення
.venv\Scripts\python app.py
```
Відкрити http://localhost:5000

## Налаштування Azure
**App registration** (Entra ID → App registrations → Payment Request System):
- Supported account types: *My organization only* (single tenant)
- Authentication → Web → Redirect URIs:
  - `http://localhost:5000/getAToken`
  - `https://paydesk.ftp.ua/getAToken` (власний домен сайту — основна адреса)
  - `https://paymentrequestsystem-ece9b4b4g0dbe7fu.polandcentral-01.azurewebsites.net/getAToken` (стара адреса App
    Service — сайт за нею теж відкривається)

**Google OAuth** (Google Cloud Console → проєкт «Payment Requests» → Credentials → клієнт «Payment Requests web») →
Authorized redirect URIs: `https://paydesk.ftp.ua/auth/google/callback`, стара адреса App Service з тим самим шляхом і
`http://localhost:5000/auth/google/callback`. Адресу повернення сайт будує з домену, на який зайшли, тож новий домен
сайту треба спершу додати сюди (інакше Google: «redirect_uri_mismatch»).

**App Service** → Environment variables:
| Name | Value |
|---|---|
| CLIENT_ID | Application (client) ID |
| TENANT_ID | Directory (tenant) ID |
| CLIENT_SECRET | client secret |
| FLASK_SECRET_KEY | випадковий рядок |
| REDIRECT_URI | `https://paydesk.ftp.ua/getAToken` |
| APP_BASE_URL | `https://paydesk.ftp.ua` — адреса сайту в листах і Telegram (фонові задачі) |
| PYTHON_ENABLE_GUNICORN_MULTIWORKERS | `true` — інакше App Service не бере дві змінні нижче |
| PYTHON_GUNICORN_CUSTOM_WORKER_NUM | `1` — один процес (`gunicorn.conf.py`: чому) |
| PYTHON_GUNICORN_CUSTOM_THREAD_NUM | `8` — потоки: запити обробляються паралельно |
| SCM_DO_BUILD_DURING_DEPLOYMENT | `true` |

Startup command — порожня: команду запуску gunicorn генерує Oryx (`Generating gunicorn command for 'app:app'` у лозі).
Файл `gunicorn.conf.py` там не читається, а власний `GUNICORN_CMD_ARGS` Oryx перезаписує своїм — тому кількість процесів
і потоків задається лише трьома змінними `PYTHON_*` вище. Перевірка — у лозі запуску (Kudu, `LogFiles/*_default_docker.log`):
`Using worker: gthread`; `Using worker: sync` означає один запит за раз (усі, зокрема Health check, чекають у черзі).

## Структура коду
- `app.py` — лише створення й налаштування додатку (gunicorn `app:app`).
- `web/` — сторінки: blueprints `requests_routes.py` (заявки), `lists_routes.py` (погодження, усі заявки, відділ),
  `payments_routes.py` (оплати), `settings_routes.py` (налаштування сповіщень), `admin_routes.py` (адмінка),
  `api_routes.py` (бот, `/health`); спільне — `auth.py` (вхід і ролі), `listing.py` (фільтри, періоди, підсумки),
  `request_helpers.py` (форма заявки, маршрут, документи), `formatting.py`, `context.py`, `errors.py`, `background.py`.
  Назви маршрутів — з префіксом blueprint: `url_for("requests.request_card", …)`.
- `workflow.py` — правила процесу; `storage/` — сховище заявок; `db_sql.py` / `db_schema.py` — база;
  модулі довідників і налаштувань (`app_settings.py`, `organizations.py`, `counterparties.py`…).

## Налаштування (адмінка)
«Адміністрування → Налаштування» — вкладки Заявка й погодження · Відділи · Оплата й готівка · Сповіщення ·
Інтеграція з 1С (звірка й API) · Система й дизайн · Журнал змін. На вкладці може бути кілька розділів
(`settings_schema.PAGES`); `?tab=<розділ>` відкриває вкладку з ним. Кожне налаштування описане один раз у
`settings_schema.py` (назва, розділ, тип, межі, значення за замовчуванням) — звідти й `app_settings.DEFAULTS`, і
перевірка форми, і підписи в журналі. Нове налаштування: додати `Setting(...)` у реєстр і поле у шаблон розділу
(`templates/admin_settings/_<розділ>.html`).
- Форма розділу змінює лише свої налаштування (сусідній розділ на тій самій вкладці не чіпає); неправильне значення —
  нічого не зберігається, пояснення вгорі.
- **Журнал змін** (`settings_log.py`, таблиця `settings_log`): хто, коли, що було → стало; пароль — «••••».
- **Резервна копія** («Система й дизайн»): «Завантажити налаштування» (JSON без пароля SMTP) і «Завантажити з файлу» —
  спершу перелік змін «було → стало», потім «Застосувати».
- Пошта (SMTP) і організації мають власні форми на своїх вкладках.
- **Заявка → Вимоги перед відправкою** (`request_helpers.submit_requirements`, лише при «Відправити на погодження»):
  документ — не обов'язковий / завжди / від суми (у валюті порогу фіндиректора, за курсом 1С); дата оплати не раніше
  ніж через N робочих днів (субота й неділя не рахуються); рядки рахунків обов'язкові.
- **Заявка → Дії автора**: «Відкликати» — вимкнено / до першого рішення погоджувача / до повного погодження;
  «Скасувати» — вимкнено / лише чернетка й доопрацювання / до «До оплати».
- **Заявка → Документи**: дозволені формати й максимальний розмір файлу (1–25 МБ) — і на сервері, і в браузері.
- **Сповіщення → Нагадування погоджувачам** (`background.run_approver_reminders`, фонова задача раз на годину з орендою):
  якщо заявка на етапі погодження довше N днів — лист / Telegram тим, у кого вона в черзі, далі кожні N днів, не більше
  M разів за етап (новий етап — з нуля); за бажанням — копія фіндиректору, коли чекає бухгалтера. Особиста подія
  «Нагадування: заявка довго чекає мого рішення». У тестовому режимі не надсилаються. 0 днів — вимкнено (за замовчуванням).
- **Оплата й готівка**: кількість нагадувань про передачу готівки (`handover_max_reminders`, за замовчуванням 5).

## Листи про помилки
`alerts.py`: необроблена помилка сторінки (користувач бачить «Щось пішло не так») або збій фонової задачі —
лист адміністраторам (група «Адміністратор» + `ADMIN_EMAILS`) з адресою сторінки, користувачем і технічним описом
(без даних форм). Та сама помилка — не частіше ніж раз на годину для всіх процесів. Надсилається, коли налаштовано
SMTP, незалежно від «Розсилка увімкнена»; вимикається в «Email-сповіщення». Записується в журнал сповіщень.

## Журнал роботи сайту
Щоб бачити, що гальмувало чи падало, — три рівні:
- **«Адміністрування → Журнал роботи»** (`ops_log.py`, таблиця `ops_log`, 30 днів): запити, довші за 3 с
  (`web/request_timing.py`: метод і шлях без параметрів, код, хто), кожен запуск фонової задачі (`jobs.run`,
  «Синхронізувати зараз», звірка після платіжки з обробки) з тривалістю й підсумком, старти сайту (за скільки
  завантажився додаток і коли прийшов перший запит — після деплою чи зміни налаштувань сайт стартує ~1 хв) і помилки
  (`alerts.report`, навіть коли листи вимкнено). Угорі — підсумок: останній старт, остання звірка, повільні запити й
  помилки за добу. У повільному запиті — куди пішов час: звернення до бази (і нові з'єднання), до Power BI.
  Довідники з Power BI (контрагенти тощо) — окремими записами: рядків, запит, розбір.
- **Профіль сторінки** — адміністратор відкриває її з `?_profile=1` (наприклад, `/requests/2?_profile=1`): у журналі
  («Профіль запиту») — функції, що забрали найбільше часу, повний звіт cProfile — у Kudu, `/home/LogFiles/paydesk-profiles`.
- **Лог App Service** — кожен запит (стандартний рядок gunicorn, без тривалості: формат з `gunicorn.conf.py` на App
  Service не діє) і старти сайту. Видно в «Log stream» і в Kudu, `LogFiles/*_default_docker.log`.
- **Перевірка доступності** — App Service → Health check (шлях `/health`, щохвилини) і правило оповіщення Azure Monitor
  `PayDesk-site-down` (група дій `PayDesk-admins`, лист на `od@ftpua.com`): «Health check status» у середньому менше
  50% за 15 хвилин, тобто сайт не відповідає ~8 хв і довше (перезапуск після деплою — ~1 хв — листа не дає). Ловить
  те, чого сам сайт записати не може: процес завис чи впав. Проблеми домену чи сертифіката (перевірка йде зсередини
  Azure) — ні; для них — платний availability test в Application Insights.

## Ролі та вхід
Ролі (Адміністратор, Ініціатор, Бухгалтер — готівка / резиденти / нерезиденти, Фіндиректор) зберігаються в самій
системі (`user_roles`: у базі, без бази — `/home/data/user_roles.json`) і змінюються в «Адмініструванні →
Користувачі й ролі → картка користувача». Зміни діють одразу. Групи Azure й Microsoft Graph не використовуються
(змінні `GROUP_*` і дозволи `GroupMember.*` / `User.ReadBasic.All` можна видалити). Людину на вході знаходять за
поштою, тож однаково працює вхід і через Google, і через Microsoft; записи, колись перенесені з Azure, мають
id = Entra object id — заявки й налаштування цих людей лишаються їхніми.

`ADMIN_EMAILS` (за замовчуванням `od@ftpua.com`) — завжди адміністратори, навіть без ролі в системі.
Керівник відділу й «бачить заявки відділу» — призначення в картці (оргструктура), не окремі ролі.

**Новий співробітник:** «+ Додати користувача» → повна робоча пошта → ролі → «Зберегти». Ім'я, якщо його не
вказали, оновиться з акаунта Google на першому вході.

**Зовнішній користувач** (пошта не з домену компанії, напр. підрядник): додає лише адміністратор — так само,
за повною поштою; у списку позначка «Зовнішній». Людина входить через посилання «Увійти іншим акаунтом Google»
(під кнопкою Google) своїм акаунтом Google з цією адресою (Gmail, Google Workspace своєї компанії або
Google-акаунт, створений на свою пошту: accounts.google.com → «Створити акаунт» → «Використати наявну адресу»).
Кого не додали або в кого не лишилося жодної ролі — Google-вхід не пускає. Через Microsoft зовнішні не входять
(додаток зареєстровано лише для тенанту компанії).

«Налаштування → Система й дизайн → Вхід у систему» (`login_methods`):
- **Google і Microsoft** (за замовчуванням);
- **Лише Google** — через Microsoft входять тільки `ADMIN_EMAILS` (запасний вхід: `/login?method=microsoft`, кнопки на
  сторінці входу немає).

Змінні App Service для Google (без них — лише вхід через Microsoft):
- `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` — OAuth-клієнт «Web application» у Google Cloud Console
  (доступ до консолі адміністратора Workspace не потрібен; OAuth consent screen — External, щоб входили й зовнішні);
- `GOOGLE_ALLOWED_DOMAINS` — домени пошти компанії через кому, напр. `ftpua.com` (без них Google-вхід вимкнено).

Authorized redirect URI клієнта: `https://<сайт>/auth/google/callback` (локально `http://localhost:5000/auth/google/callback`).
Сторінка входу — `/login`, вихід — `/auth/logout` (Google — забути сеанс; Microsoft — ще й вихід із Microsoft).

Маршрут погодження: Ініціатор → Бухгалтер → Фіндиректор → Оплата. Режим задається в «Адмініструванні →
Налаштування процесу» (`data/app_settings.json`, на Azure — `/home/data/`):
- **послідовно** — фіндиректор отримує заявку після погодження бухгалтера;
- **паралельно** — заявка одразу в обох (статус «На погодженні»), до оплати — коли погодили обидва.
Режим запам'ятовується в заявці під час відправки: зміна діє на нові та повторно відправлені заявки.

Коментарі: кожен, хто бачить заявку, може залишити коментар на будь-якому етапі — статус не змінюється,
коментар потрапляє в історію.
Бухгалтер (і перевірка, і оплата) визначається формою оплати та організацією заявки:
- Готівка → бухгалтер готівки (для будь-якої організації);
- Безготівка + організація-резидент (напр. ФТП) → бухгалтер резидентів;
- Безготівка + організація-нерезидент (напр. Litbia) → бухгалтер нерезидентів.

Резидентність організації — з довідника 1С (країна Україна — резидент). Організації можна призначити іншого
бухгалтера: «Адміністрування → Організації → Готівка / Безготівка — хто перевіряє» (напр. ФОП, якого веде бухгалтер
готівки). Призначення діє одразу й на заявки в роботі; колонка «Форма оплати» у списках не змінюється.

**Що робить бухгалтер** (картка користувача, пункт 1 — блок «Бухгалтер», `user_roles.acc_mode`):
- **«Погоджує і оплачує»** (за замовчуванням) — як описано вище: «На погодження» й «До оплати», сповіщення про обидва;
- **«Лише оплачує»** (`RoleSet.pay_only`, `wf.pays_only`):
  - не погоджує й не бачить заявок на погодженні: пункту «На погодження» немає, картка такої заявки — 404,
    `/approvals` веде на «До оплати»;
  - бачить «До оплати» й оплачені свого виду, а також свої заявки, якщо він ще й ініціатор; головна — «До оплати»;
  - сповіщення — лише «До оплати» (у журналі сповіщень — чому про погодження не надіслано), нагадувань погоджувачам немає.

Якщо в якогось виду бухгалтера всі «Лише оплачує», зберегти можна, але картка й «Користувачі та ролі» показують
попередження: заявки цього виду нікому погодити. Склад ролей для розсилки після збереження картки перечитується одразу.

**Шапка на телефоні** (до 760 px): розділи — за кнопкою «☰» (на ній — сума «На погодження» й «До оплати»),
розгортаються вертикальним списком; закриваються вибором пункту, кліком поза меню або Esc.

### Форма заявки
Поля згруповано в блоки за порядком заповнення: 1 — кому і за що (контрагент, стаття, відділ), 2 — скільки і коли
(сума разом із валютою, дата оплати з кнопками «Сьогодні / наступний робочий день / через тиждень» з урахуванням
найранішої дати, форма оплати), 3 — хто платить (організація / платник / бухгалтер), 4 — рахунки (і різниця з
сумою заявки), 5 — примітка; обов'язкові поля позначено «*». Праворуч (на телефоні — внизу) — панель «Підсумок»:
сума, контрагент, стаття, відділ, дата; «Погоджуватимуть» — маршрут для поточних даних
(`/requests/route-preview`, ті самі правила, що й при відправці: налаштування відділу, поріг керівника, фіндиректор);
«Що ще заповнити» — обов'язкові поля й вимоги з налаштувань; кнопки «Відправити», «Записати», «Записати й закрити».

### Звірка з платежами 1С
«Налаштування → Інтеграція з 1С» (`payments.py`, `payment_match.py`). Платежі (документи списання, банк і каса) — з таблиці
Power BI `Payments` (`PBI_PAYMENTS_TABLE`; рядок = рядок розшифровки): копія в базі PayDesk (`payments`,
`payment_links`, `payment_issues`), перше завантаження — по місяцях від «Звіряти платежі з», далі кожні N хвилин лише
змінені документи (`RowVersion`) і перевірка зниклих (видалених у 1С зовсім) за 14 днів, раз на добу — за 90 днів;
«Синхронізувати зараз» в адмінці (зниклі — за 90 днів). Платіжку, створену обробкою 1С (`created`), PayDesk забирає за
30 секунд (`background.payments_sync_soon`), не чекаючи розкладу: тоді звірка помітить, навіть якщо документ невдовзі
видалять зовсім. N — «Синхронізувати
з 1С кожні» (`payments_sync_minutes`, 5–120, за замовчуванням 10); фоновий потік щохвилини перевіряє, чи пора
(`payments.sync_due`), тож новий інтервал діє одразу. Нові платіжки видно, коли вони вже є в Power BI. Без Power BI або
в тестовому режимі — демо-платежі (`storage/demo.py`).

**Сума платежу** для звірки — сума документа (шапка), колонка `DocumentAmount` у таблиці Power BI
(`p._Fld7996 AS DocumentAmount` у запиті до `_Document7811`): рядки «Счета» можуть бути меншими — решта лишається
авансом. Без цієї колонки — сума рядків (`Amount`). Коли колонка з'являється, PayDesk один раз дописує суми документів у
наявну копію легким запитом (стан `doc_amount`), без перезавантаження; прив'язки до заявок лишаються.

**Номер заявки для людей** (`request_numbers.py`; «Налаштування → Заявка → Номер заявки»): префікс (до 6 латинських
літер) і кількість цифр з нулями попереду — лише показ: у базі номер той самий (`000000123`), тож нове налаштування
одразу діє для всіх заявок. За замовчуванням — без префікса, 9 цифр (як було). Позначка заявки в призначенні платежу й
Примечании 1С (`marker`): з префіксом — `PD000123`, без — `#123`. Колишні префікси зберігаються
(`request_prefix_history`) і розпізнаються далі. Номер розпізнається в будь-якому вигляді: після `#` (`#123`, `# 123`,
`#000123`, `#PD123`), з префіксом без `#` (`PD123`, `PD000123`, `PD-123`, `PD 123`, `pd123`, кирилична «Р» замість «P»),
але не всередині слова (`UPD123`) і не голим числом (у призначенні — номери рахунків, суми). У пошуку PayDesk номер з `#`
чи префіксом шукається точно, голе число — як раніше. Тест — `request_numbers_test.py`.

Зіставлення: спершу номер заявки в призначенні (`#5` чи `PD000005` → заявка 000000005; кілька номерів — один платіж на кілька заявок):
збігаються валюта, сума й (для безготівки) контрагент — прив'язка, інакше розбіжність; без `#` — за сумою, валютою,
контрагентом (для готівки — або одержувач-автор), видом оплати й датою. Кандидати — заявки «До оплати» й оплачені без
платежу за останні 130 днів (вікно платежів, 120 днів, + 10), а не всі з «Звіряти платежі з» — інакше їх щодня більше.
Режим «Оплачено» для кожного виду бухгалтера (`pay_mode_acc_*`): «Вручну» — платіж лише прив'язується;
«Автоматично» — «Оплачено» ставить звірка (кнопки «Оплачено» немає, у картці підказка `#номер`); «Обидва».
Платіж, прив'язаний до заявки, видалили, розпровели або він зник з 1С — зв'язок зникає, а заявка без інших активних
платежів знову «До оплати» (історія `payment_removed`; відмітка обробки 1С про цей документ знімається, тож обробка
знову запропонує платіжку). Так само — для заявки, яку оплатила обробка 1С, якщо її документ видалили ще до прив'язки.

Звіт «Звірка» (`/payments/reconcile`, фіндиректор і адміністратор; у меню — кількість платежів без заявки за 30 днів):
плитки-вкладки «Без заявки», «Розбіжності» (`#номер` не збігся — з посиланням на заявку й порівнянням суми та
контрагента; кілька кандидатів), «Зіставлені з заявками» (яка заявка, як знайдено, хто
поставив «Оплачено») і «Дозволені без заявки»; блок «Як працює звірка»; фільтр за видом оплати (банк / каса / рахунок).
Винятки (`payments_ok_*`): вид операції 1С, вид оплати, стаття витрат або **відділ статті** (відділ, до якого в довіднику
прив'язано статтю); адміністратор додає виняток і з рядка звіту («Дозволити без заявки…», `POST /payments/allow`).
Кожен виняток може мати дату **«діє до»** (`payments_ok_until`): платежі до неї включно дозволені, пізніші знову
потребують заявки — так виняток вимикають, не перераховуючи минулих платежів; без дати — назавжди.

**Поступове підключення відділів.** «Відділи → Звірка з 1С»: для відділу — дата «заявки обов'язкові з»
(`dept_settings.requests_since`). Відділ — той, що в самому документі списання 1С (рядки розшифровки). Платіж такого
відділу раніше дати — «Дозволені без заявки» («Відділ ще не працює через PayDesk»), з дати — звичайна звірка. Відділи без
дати — за режимом `payments_dept_default`: «уже працюють» (за замовчуванням, як раніше) або «ще не працюють». Якщо в
документі кілька відділів, заявка не потрібна, лише коли жоден із них ще не підключено; документ без відділу
звіряється як звичайно. Ручна прив'язка платежу до заявки (`payment_link_roles`: бухгалтер заявки,
фіндиректор, адміністратор) — у звіті вибором зі списку («Знайти заявку…», кандидати — `GET /payments/link-candidates`:
спершу з #номером у призначенні, далі той самий контрагент і сума) й у картці заявки (режими «Автоматично» й «Обидва»);
заявка «До оплати» стає оплаченою. Адміністратор може відв'язати платіж у картці. Біля оплачених заявок, зв'язаних із
платежем, у списках — «платіж № …».

### API для 1С
Обробка 1С сама забирає з PayDesk заявки «До оплати» й (згодом) повідомляє, що створила платіжку. PayDesk у 1С нічого
не пише. Обробки 1С у цьому репозиторії не зберігаються. ТЗ для підрядника:
https://claude.ai/artifact/4gPu29wSUJgq3iWUzg4Q2q.

Логіка — `onec_api.py`, маршрути — `web/onec_api_routes.py` (без CSRF і сеансу входу).

**Доступ.** «Налаштування → API для 1С»: увімкнення, дозволені IP і ключ `X-Api-Key`. Ключ показується один раз, у
PayDesk зберігається лише SHA-256, новий ключ скасовує старий.

**Помилки.** Відповіді — JSON (UTF-8); помилка — `{"ok": false, "error": "текст"}` з кодом:
- 403 — API вимкнено, невірний ключ або IP не дозволено;
- 404 — немає заявки;
- 409 — заявка не «До оплати» або вже є інша платіжка;
- 400 — неповні дані.

| Метод | Шлях | Що робить |
|---|---|---|
| GET | `/api/1c/v1/ping` | перевірка зв'язку й ключа |
| GET | `/api/1c/v1/payment-orders?state=new&form=bank` | заявки у форматі платіжки |
| GET | `/api/1c/v1/payment-orders/<id>` | одна заявка |
| POST | `…/<id>/created` | 1С створила платіжку: `{"doc_number", "doc_date", "doc_ref", "doc_type", "user", "posted"?, "replace"?}` |
| POST | `…/<id>/failed` | 1С не змогла: `{"message", "user"}` |
| POST | `…/<id>/reset` | платіжку в 1С видалили — заявка знову «нова» |
| GET | `/api/1c/v1/payment-checks?since=2026-10-01` | заявки «До оплати» й оплачені з дати — з прив'язаними платежами 1С, для перевірки документів |

**`posted: true`** — платіжку створено проведеною: якщо для бухгалтера заявки «Оплачено» ставиться автоматично
(«Автоматично» / «Обидва»), заявка одразу «Оплачено» (історія — від імені користувача 1С, передача готівки й листи — як
при звичайній оплаті); звірка потім лише прив'яже платіж за `#номером`. У режимі «Вручну» — лише відмітка.

**Перевірка документів** (`payment-checks`, за замовчуванням `since` — 30 днів тому). Поля — як у платіжки, плюс
`payments[]`: документи 1С, які звірка вже прив'язала до заявки — `doc_ref` (посилання 1С), `guid`, `number`, `kind`
(`Bank` / `Cash`), `date`, `active` (проведений і не видалений), `match` (`number` / `auto` / `manual`). У відповіді
ще `prefixes` — префікси номера заявки (поточний і колишні). Обробка 1С порівнює з заявкою ці документи й документи з
номером заявки в примечании (`#15` або з префіксом: `PD000015`, `PD-15`) і виправляє в 1С контрагента, статтю,
відділ, співробітника. Рядки рахунків («Счета») не порівнюються: бухгалтер може виправити рахунок у платіжці вручну.
PayDesk нічого не надсилається: звірка сама перечитає змінений документ.

**Фільтри списку.**
- `state`:
  - `new` — без платіжки;
  - `failed` — з помилкою;
  - `created` — платіжку створено;
  - `cancelled` — платіжку створено, а заявку повернули;
  - `all` — усі «До оплати».
- `form` — `bank` / `cash`.
- `organization` — код, GUID або ref.

**Поля платіжки.**
- `request_id`, `number` (як у базі, `000000015`), `number_label` (для людей, `PD000015`), `marker` (позначка для
  Примечания: `PD000015` або `#15`), `markers` (усі позначки — нові й колишні, — за якими шукати вже створену платіжку);
- `status`, `payment_form`, `pay_date`;
- `amount`, `currency`, `currency_ref`;
- `organization`, `payment_type`, `counterparty` (`in_1c` — чи вже в 1С), `expense_item`, `department`;
- `invoices[]`;
- `purpose` (у кінці `marker` — для звірки);
- `payment_kind` — `contractor` (оплата рахунків підрядника) або `indirect` (непряма витрата);
- `note`, `author` (`name`, `email`, `employee` — співробітник 1С: `guid`, `ref`, `code`, `name`), `approved_at`, `url`;
- `onec_state` / `onec_order` — остання відмітка 1С. Вона зберігається в `req["onec_order"]`, видно її в картці заявки
  й у «До оплати», кожна зміна — в історії.

**`guid` і `ref`.** `guid` — як у SQL-базі 1С (`_IDRRef`, 32 hex). `ref` — той самий ідентифікатор як
`УникальныйИдентификатор` 1С (байти переставлені: `h[24:32]-h[20:24]-h[16:20]-h[0:4]-h[4:16]`), тож
`Справочники.X.ПолучитьСсылку(Новый УникальныйИдентификатор(ref))`.

### Дизайн
«Налаштування → Дизайн → Назва системи» (`app_name`, за замовчуванням «PayDesk»): шапка, заголовки вкладок браузера,
сторінка входу, листи, ярлик на телефоні (`/site.webmanifest`). Ім'я відправника листів — окремо (`mail_sender_name`).

Порядок полів у всіх дизайнах — як вони залежать одне від одного: **відділ** (лише якщо в автора кілька відділів
для заявок; основний підставлено; один відділ — пункту немає, він у шапці заявки) → **що оплачуємо** (якщо у відділі
є прямі витрати) → **кому і за що** (контрагент, стаття) → **рахунки** (пряма витрата; заповнюють суму) → **скільки
і коли** → **хто платить** → **примітка**. Зміна відділу після підбору рахунків питає, чи прибрати їх (вони — іншого
відділу). Номери блоків класичної картки рахує CSS лише по видимих блоках.

«Налаштування → Дизайн»: дизайн картки заявки (`card_design`) — класична (блоки й панель «Підсумок»), покроковий
майстер (один крок на екрані: що оплачуємо → кому → рахунки → сума й оплата → перевірка й відправка) або чек-лист
(розділи на одній сторінці згортаються в рядок-підсумок, унизу — сума, маршрут і кнопки). Поля спільні
(`templates/request/_*.html`), логіка кроків — `static/request-steps.js`; заявку, яку редагувати не можна, нові дизайни
показують коротким переглядом (`request/_view.html`). «Приклад» (`/admin/settings/design/preview`) відкриває картку
з прикладом даних у будь-якому дизайні й темі — заповнення або перегляд бухгалтером; нічого не зберігається.

Кольорова тема всієї програми (`color_theme`) — синя (стандартна), темна, смарагдова, графіт
з фіолетовим; для всіх користувачів. Тема — атрибут `<html data-theme>` (`web/context.py`), кольори — змінні CSS
у `static/style.css` (`:root` — синя, `html[data-theme=…]` — інші). На вкладці — мініатюра кожної теми й «Спробувати»
(показує тему на сторінці до збереження). Сторінки до входу (вхід, конфіденційність, помилка) і листи — без теми.

**Святкове оформлення** (`holidays`, `holiday_now`; календар — `holidays.py`): відмічені свята з'являються самі у свої
дні за київським часом — Новий рік і Різдво (15.12–14.01), Великдень (тиждень до й день після, православна пасхалія),
День вишиванки (3-й четвер травня), День бухгалтера (14–16.07), День Незалежності (22–24.08), 8 Березня, День
закоханих, Хелловін; «Показати зараз» — будь-яке свято вручну. Прикраси — `static/holiday/*.svg` через CSS
(`<html data-holiday>`, змінні `--hd-*`): смуга й «небо» в шапці, деталь на логотипі, предмети й привітання біля
меню, куток картки заявки; нічого не перекривають, без анімації при `prefers-reduced-motion`.

### Тип оплати й рахунки з 1С
«Налаштування → Заявка → Рахунки в заявці» (`invoices_mode`, за замовчуванням увімкнено). Увімкнено — перший крок
заявки «Що оплачуємо?» (кнопки з поясненням під ними; доки не вибрано, решта форми прихована й сервер заявку не приймає):
- **Пряма витрата** — оплата рахунку підрядника за угодою профітцентру (послуги для клієнта в собівартості). Стаття —
  зі статей прямих витрат відділу заявки («Налаштування → Відділи»: свій список або за замовчуванням,
  `contractor_expense_codes`, спершу CR000065 «Оплата рахунку»); блок «Рахунки» з «Підбором рахунків» з 1С; рахунки
  обов'язкові, якщо так задано для відділу (або загальним «Рядки рахунків обов'язкові»);
- **Непряма витрата** — утримання компанії: статті з бюджету людини, без рахунків.
Хто може робити прямі витрати — «Відділи → Прямі витрати»: за замовчуванням профітцентри (Profitcenter у 1С), можна
дозволити чи заборонити кожному відділу. Відділ без прямих — кроку немає, заявка одразу непряма.
Питання можна вимкнути («Питання «Що оплачуємо?» у заявці», `kind_question`) — якщо менеджерам важко визначити тип:
тоді в списку статті, дозволені користувачу, а тип заявки визначає стаття (пряма стаття відділу з прямими витратами —
пряма витрата). Блок «Рахунки» без питання — за `invoices_block`: показувати завжди, не показувати або за статтею.
Вимкнено — без типу й рахунків, статті з бюджету (збережені раніше рахунки лише показуються).

«Підбір рахунків» (`invoices.py`, `/requests/invoices`): таблиця `InvoiceForPay` (`PBI_INVOICES_TABLE`) — DAX-запит
лише рахунків вибраного контрагента (`CounterpartyGUID`) **й відділу заявки** (`DepartmentGUID`; рахунки інших відділів
і без відділу не показуються) з залишком до оплати (`UnpaidAmountInCurrency > 0`), від найстаріших до найновіших
(FIFO); кеш 5 хв. Рядки додаються лише з підбору. У вікні — пошук, «Вибрати всі», сума вибраних; рахунок, що вже є в
іншій заявці в роботі (не відхиленій і не скасованій), позначено «вже в заявці № …» (додати можна з підтвердженням).
Рядок отримує номер, залишок (можна зменшити — часткова оплата), валюту й угоду; порожня сума заявки заповнюється сумою
рахунків.

**Лише у валюті заявки й не більше за суму.** Рахунки в інших валютах у підборі не показуються (підказка, скільки їх;
поки рахунків не додано — кнопка «Змінити валюту заявки на …»), валюту рядка не вибирають. Рахунки разом не можуть
бути більшими за суму заявки: «Додати вибрані» вимкнено, під таблицею — червона підказка; менше можна — решта
лишається авансом. Те саме перевіряє сервер при збереженні й відправці (`lines_error`): рядок в іншій валюті (старі
заявки) або більша сума — помилка в блоці рахунків.

### Відділи, керівник відділу, учасники заявки
Усі налаштування людини — в її **картці** («Адміністрування» → клік по людині або «+ Додати користувача» →
пошта → картка): ролі, відділ співробітника, на які відділи подає заявки / які очолює / заявки яких бачить,
статті бюджету, з поясненнями до кожного пункту й однією кнопкою «Зберегти» (`/admin/users/<id>`).

**Співробітники з 1С** («Користувачі й ролі → Співробітники з 1С», `/admin/users/onec`, `onec_sync.py`):
- «Ще не в системі» — працюючі співробітники з поштою (`Employees`), яких немає в системі; «Додати вибраних»
  дає за **правилом** (на цій же сторінці; за замовчуванням роль «Ініціатор» і статті свого відділу): ролі, основний
  відділ із 1С, керівника відділу (`DepartmentHead` = 1; попередній керівник відділу замінюється), статті з розподілом
  свого відділу (відділи статей за `DepartmentGUID`), співробітникам **профітцентрів** (`Departments.Profitcenter`) —
  ще й прямі статті, бухгалтеру — користувача 1С (`UserPaymentTypes.EmployeeGUID`);
- «Уже в системі» — розбіжності з 1С (відділ, керівник відділу, користувач 1С бухгалтера): «Взяти з 1С»;
  «Застосувати правило» лише додає ролі й статті, нічого не знімає;
- «Звільнені в 1С, але з доступом» (`IsDeleted`) — «Закрити доступ» знімає всі ролі (заявки й історія лишаються).
Усе це потім можна змінити в картці людини (зокрема прибрати чи додати прямі статті).

**Автоматично** (галочка в правилі, `onec_auto_sync`; фонова задача раз на годину, одразу після ввімкнення й після
«Оновити зараз»): нові співробітники з **корпоративною** поштою (`GOOGLE_ALLOWED_DOMAINS`) додаються за правилом,
звільненим закривається доступ. З особистою поштою — лише вручну; розбіжності в тих, хто вже є, — лише показуються;
кому доступ уже закрили, повторно не додається. Запобіжники: без довідника співробітників (помилка Power BI, порожньо)
нічого не робиться; якщо звільненими позначено понад 10 людей і понад 20 % користувачів — доступ не закривається,
адміністраторам іде лист. Остання синхронізація й її підсумок — на сторінці.

Окремі, незалежні налаштування:
- **Відділ співробітника** (картка, пункт 2) — основний відділ людини (з 1С: `Employees.DepartmentGUID`; картка
  підказує, якщо в системі інший). Довідник — `Departments` (`departments.py`).
- **Відділ заявки** — поле «Відділ» у заявці: ініціатор вибирає з відділів, на які подає заявки (картка, пункт 3,
  колонка «Подає заявки»; основний — завжди). Один відділ — поле без вибору. Керівник **вибраного** відділу бачить
  заявку в «Заявках відділу» і погоджує її; зміна відділу записується в історію. «Мої заявки» показують колонку й
  фільтр «Відділ», якщо відділів кілька; бухгалтери, фіндиректор і адміністратор бачать усі відділи в списках.
- **Керівництво й перегляд відділів** (картка користувача, пункт 3; `org_structure`; керівника можна взяти з 1С): у кожного відділу **один керівник**
  (одна людина може очолювати кілька відділів) і список тих, хто **бачить заявки відділу** (заступники, менеджери).
  Це не групи Azure: ролі «Керівник відділу» / «Перегляд заявок відділу» з'являються під час входу самі.
  Керівник і ті, хто бачить, мають розділ «Заявки відділу» (без чернеток) і можуть коментувати.
  Якщо керівника змінити — заявки, що чекають його погодження, переходять до нового.
- **Погодження керівником** — у «Налаштуваннях процесу»: «лише бачить» або «погоджує першим кроком»
  (далі послідовно або паралельно). Автор-керівник свого відділу — крок зараховується автоматично;
  без відділу чи без керівника — крок пропускається (запис в історії).
- **Налаштування відділів** («Налаштування → Відділи», `dept_settings.py`), для кожного відділу:
  керівник погоджує / лише бачить / як у загальних налаштуваннях; **поріг керівника** (у валюті порога фіндиректора за
  курсом 1С; дрібніші заявки йдуть одразу до бухгалтера, з записом в історії); **заступник погоджує** — ті, хто бачить
  заявки відділу, погоджують замість керівника (листи «чекає рішення» — і їм; свою заявку заступник не погоджує);
  **фіндиректор** — за загальними правилами або завжди. Маршрут фіксується під час відправки; зміни — у журналі змін.
- **Учасники заявки** (як «копія» в листі): автор або адмін додає колег зі списку користувачів системи.
  Учасник бачить заявку (і чернетку), коментує, додає файли й отримує ті самі листи, що й автор
  («Вас додано до заявки…» — першим); редагує й відправляє заявку лише автор. Вкладка «Мої заявки → Я учасник».
- **Статті бюджету** — як і раніше, окремо для кожного користувача.

### Організація в заявці
«Налаштування процесу → Організація в заявці»: **«Організація»** (ініціатор вибирає зі списку, як раніше) або
**«Платник»** — ініціатор вибирає лише «Українська компанія / Іноземна компанія» (`req["payer"]`), цього достатньо,
щоб визначити бухгалтера. Організацію в такій заявці не вказує ніхто; у списках і листах — «Українська компанія» /
«Іноземна компанія». Призначення бухгалтерів організаціям («Організації») діє лише для заявок з організацією.
**«Бухгалтер»** — ініціатор одразу вибирає тип бухгалтера (по готівці / резидентів / нерезидентів, `req["accountant_type"]`);
заявку бачать і опрацьовують усі люди з цією роллю. Вибраний тип має пріоритет над правилами й призначеннями.
У новій заявці тип підставляється з картки користувача («Бухгалтер за замовчуванням», задає адмін), а якщо не задано —
як у попередній заявці ініціатора; ініціатор може змінити.

### Фіндиректор і нові контрагенти
- **Фіндиректор** («Налаштування процесу → Фіндиректор»): «Погоджує» (як раніше) або «Лише спостерігає». Тоді погоджує
  тільки бухгалтер (порядок «послідовно / паралельно» не діє). Фіндиректор не отримує заявок на рішення, але бачить
  «Усі заявки» (лише перегляд), «До оплати», «Оплачені» й картку кожної заявки. Вибір запам'ятовується в заявці при
  відправці (`cfo_step`): заявки, відправлені раніше, проходять свій маршрут.
- **Фіндиректор «Погоджує за правилами»** (`cfo_rules.py`): таблиця за типом бухгалтера заявки — бухгалтер по готівці,
  резидентів, нерезидентів: «завжди», «від суми» або «ніколи»; поріг у USD, EUR чи UAH за останнім відомим курсом 1С на
  момент відправки (`rates.convert`, таблиця `ExchangeRates`: Date, GUID валюти, RateBU — гривень за 1 од.; читаються
  лише останні 31 день; курсу немає — фіндиректор погоджує). Додатково — незалежно від таблиці — заявки з новим
  контрагентом (ще немає в 1С) і зі статтями зі списку. Рішення — `cfo_step`, пояснення (яке правило спрацювало) —
  запис «Поріг фіндиректора» в історії. Поки таблицю не збережено, усі рядки — «від суми» з `cfo_threshold_usd`.
- **Фіндиректор як керівник бухгалтерів** (у будь-якому режимі): «На погодження → У бухгалтерів» — усі заявки, що чекають
  бухгалтерів; у картці — «Втручання фіндиректора»: повернути на доопрацювання або відхилити (погоджує бухгалтер).
- **Хто заводить нового контрагента в 1С**: бухгалтер (як раніше) або адміністратор. В режимі «адміністратор» блок
  прив'язки в картці бачить лише адмін (бухгалтер — примітку), а адміністратори (група + `ADMIN_EMAILS`) отримують лист,
  коли надходить заявка з новим контрагентом. Автоприв'язка за ЄДРПОУ працює в обох режимах.

### Відкликати чи скасувати заявку (автор)
У картці власної заявки — блок «Дії автора»:
- **«Відкликати на редагування»** — поки заявку погоджують (керівник відділу, бухгалтер, фіндиректор, паралельно).
  Заявка повертається автору в чернетку, погодження скидаються (навіть якщо хтось уже погодив), після виправлення
  «Відправити на погодження» запускає маршрут з початку (режим, поріг фіндиректора, керівник відділу — заново).
- **«Скасувати заявку»** — у чернетці, на доопрацюванні або поки погоджують; причина обов'язкова. Статус
  «Скасовано» (закритий, як «Відхилено»: «Відхилено» — рішення погоджувача, «Скасовано» — рішення автора).
- Після «До оплати» автор уже не відкликає й не скасовує (повернути може бухгалтер або адмін).
- Повідомлення (подія «Заявку… автор відкликав чи скасував», за замовчуванням увімкнена) отримують ті, у кого заявка
  чекала рішення, і ті, хто вже погодив її в поточному колі; про скасування — також учасники заявки.

### Зміна статусу адміністратором
«На погодженні» лишає рішення про фіндиректора, ухвалене за сумою при відправці (поріг у USD); «Погодження
фіндиректора» — явно передає рішення фіндиректору незалежно від суми.

### Розподіл обов'язків
Параметр «Налаштування процесу → Розподіл обов'язків → Автор не може погоджувати свою заявку» (за замовчуванням вимкнено).
Коли ввімкнено, автор не ухвалює рішень по власній заявці на етапах погодження (керівник відділу, бухгалтер,
фіндиректор), навіть якщо має відповідну роль: заявки немає в його «На погодження», в картці замість кнопок —
пояснення, лист «нова заявка на погодження» йому не надсилається; втручання фіндиректора у власну заявку теж
недоступне. Оплатити вже погоджену заявку автор-бухгалтер може. Якщо погоджувач — єдина людина зі своєю роллю,
рішення по його заявці ухвалює адміністратор («Змінити статус»). Діє одразу, зокрема для заявок, що вже на погодженні.

### Готівка через автора заявки
Параметр «Налаштування процесу → Готівка через автора заявки» (за замовчуванням увімкнено):
- Готівку в касі **завжди отримує автор заявки** й передає підряднику.
- Після «Оплачено» (статус і проведення в 1С не змінюються) кожна готівкова заявка **чекає підтвердження автора**:
  дата передачі (не раніше видачі й не в майбутньому) і необов'язковий коментар, документ не потрібен.
  За автора може підтвердити бухгалтер заявки або адмін (в історії видно хто); скасувати — лише адмін, з причиною.
- **«До оплати → Готівка не підтверджена»** — лише в бухгалтера по готівці (або того, кому готівку організації
  призначено в «Організаціях»): дата видачі, скільки днів, нагадування, підсумок «у кого скільки готівки».
- **Нагадування** — лише автору, кожні N днів (параметр, 0 — вимкнено), не більше 5; особисті налаштування їх
  не вимикають. Фоновий потік перевіряє раз на годину (на F1 без Always On — коли застосунок прокинеться).
- Бухгалтер може ввімкнути собі лист «Автор підтвердив передачу» (за замовчуванням вимкнено).

## Довідник статей витрат (Power BI)
Статті беруться з семантичної моделі Power BI, таблиця `Expense_Item` (`expense_items.py`).
Доступ — від імені додатку (service principal) з тими самими `CLIENT_ID` / `CLIENT_SECRET` / `TENANT_ID`.
Користувачу показуються лише елементи: групи (за `Тип_вузла` або наявністю дочірніх рядків) приховано.

| Змінна | Значення |
|---|---|
| `PBI_GROUP_ID` | ID workspace Power BI |
| `PBI_DATASET_ID` | ID семантичної моделі |
| `PBI_TABLE` | `Expense_Item` (за замовчуванням) |
| `PBI_CACHE_MINUTES` | як часто перечитувати довідник, за замовчуванням 60 |

Налаштування Power BI (одноразово):
- Admin portal → Tenant settings → «Service principals can use Fabric APIs» → Enabled
  (можна обмежити групою безпеки, до якої додано додаток);
- Admin portal → Tenant settings → «Dataset Execute Queries REST API» → Enabled;
- Workspace → Manage access → додати `Payment Request System` (Viewer; якщо не вистачить — Contributor).

Довідник оновлюється сам: раз на `PBI_CACHE_MINUTES` хвилин у фоні (користувач не чекає Power BI —
поки йде оновлення, показується попередній список). Після перезапуску одразу береться збережена копія.

Тип статті: без відділу — **пряма**, з відділом (колонка «Відділ») — **з розподілом**; одна стаття
може мати кілька відділів.

### Статті бюджету користувачів
В «Адмініструванні» для кожного користувача задається, які статті він може вибирати в заявці:
прямі статті, усі відділи або вибрані відділи. Без налаштувань — **жодної статті**. Нові співробітники з 1С
отримують за правилом статті свого відділу (відділи статей, чий `DepartmentGUID` — їхній відділ), а співробітники
профітцентрів — ще й прямі; далі кожному можна змінити в картці.
Налаштування зберігаються у `/home/data/user_budget.json` (локально `data/`), ключ — Entra object id.

Без `PBI_GROUP_ID`/`PBI_DATASET_ID` працюють мокові статті. Остання вдала копія довідника
зберігається у `/home/data/expense_items.json`. Стан і кнопка «Оновити зараз» — в «Адмініструванні».

## База даних (Azure SQL)
`db_sql.py` + `docstore.py`. Вмикається налаштуваннями App Service (Environment variables):
`SQL_SERVER=ftp-payreq-sql.database.windows.net`, `SQL_DATABASE=payrequests`. Без них — як раніше: демо-заявки
в пам'яті, налаштування в JSON-файлах (локально, у тестах; `DATABASE_URL=sqlite:///…` — локальна SQLite).
- Вхід **без пароля**: на App Service — керована ідентичність сайту (Identity → System assigned → On), у базі —
  `CREATE USER [PaymentRequestSystem] FROM EXTERNAL PROVIDER` + ролі db_datareader / db_datawriter / db_ddladmin.
  Сервер — Microsoft Entra-only, тариф бази Basic. Потрібен ODBC Driver 17/18 for SQL Server (є в образі App Service;
  `/health` показує знайдені драйвери).
- Таблиці, нові колонки й індекси створюються самі (`db_schema.py`): `requests` (уся заявка в JSON `data` +
  похідні колонки для списків і звітів), `request_history` (лише дописується — журнал аудиту), `request_lines`,
  `request_participants`, `request_files`, `request_rev`, `request_seq`, `schema_meta`, `documents`
  (налаштування й довідники системи). Колонки ніколи не видаляються автоматично.
- **Сховище заявок** — пакет `storage/` (див. розділ нижче).
- **Перенесення**: при першому читанні кожного налаштування з базою JSON-файл із `/home/data` копіюється в базу
  (файл лишається як резервна копія). Демо-заявки в базу не потрапляють.
- Лишаються файлами: кеші довідників з Power BI, сесії входу, вкладені файли (`/home/data/uploads`).
- `/health` — стан бази (кількість заявок або помилка, 503).
- **Перемикач «Дані»** (Налаштування процесу): «Робоча база» або «Тестові дані» — демо-заявки в пам'яті на справжніх
  довідниках; що створено в тестовому режимі, у базу не потрапляє; банер для всіх; розсилка за замовчуванням вимкнена, вмикається окремо (`test_mode_mail`) — тоді «[ТЕСТ]» у темі й «🧪 ТЕСТ» у Telegram; нагадування про готівку — ніколи.
- Вимкнути базу (повернутися до файлів) — прибрати `SQL_SERVER` з налаштувань App Service.

## Сховище заявок (`storage/`)
- `storage/__init__.py` — те, чим користуються маршрути: `get_request`, `save_request`, `scope_rows` (легкі рядки
  списку), `get_many`, `count`. Робочий режим — `storage/sql.py` (база), інакше — `storage/memory.py` (демо).
- **Списки** (`storage/scopes.py`): «мої», «учасник», «черга», «до оплати», «оплачені», «опрацьовані», «відділ»,
  «усі»… Правила видимості — функції `workflow.py`; у базі для архівних списків — рівноцінні SQL-умови
  (тест `storage_equiv_test.py` порівнює обидві реалізації на тисячах комбінацій ролей).
- **Легкі рядки** (`storage/derive.py`): фільтри, пошук, кількості й суми працюють без завантаження повних заявок;
  повні — лише для показаних рядків (100 за раз, далі — «Показати ще»). У базі легкі поля — колонки таблиці,
  що перераховуються автоматично при зміні їхньої логіки (`DERIVED_VERSION`) і після збереження організацій.
- **Заявки «в роботі»** (на погодженні, до оплати, готівка не підтверджена) кожен процес тримає в пам'яті й
  оновлює за лічильником змін `request_rev` — зміни з інших процесів видно одразу, а черги й лічильники в меню
  не читають базу щоразу. Архівні списки — запитом.
- **Номер заявки** видає база (`request_seq`) при першому збереженні — унікальний для будь-якої кількості процесів.
- **Захист від одночасних змін**: у заявці `version`; збереження застарілої копії — `StaleRequestError`, а форми
  картки передають версію сторінки: якщо заявку тим часом змінили, дію не виконано, користувач бачить хто й коли.

## Файли заявок (Azure Blob Storage)
`filestore.py`. Вмикається змінними App Service `BLOB_ACCOUNT_URL=https://ftppayreqfiles.blob.core.windows.net` і
`BLOB_CONTAINER=attachments`; без них — папка `/home/data/uploads`, як раніше. Вхід без ключів — керована ідентичність
сайту з роллю **Storage Blob Data Contributor** на сховищі (анонімний доступ вимкнено, «м'яке видалення» 7 днів).
Файли з диска переносяться в Blob у фоні після запуску й при першому відкритті (копії на диску лишаються).
Скачування — лише через сайт і лише тим, хто бачить заявку. `/health` показує `files: blob` або помилку доступу.

## Сповіщення в Telegram (корпоративний бот tb_ftp)
`telegram_notify.py`. Користувач у «Сповіщеннях» вибирає: Пошта / Telegram / Пошта і Telegram. Бот (Heroku, worker)
сам забирає повідомлення кожні ~30 с: `GET /api/telegram/outbox`, підтверджує `POST /api/telegram/ack`
(sent / not_found / blocked / failed), раз на 10 хв передає список знайдених людей `POST /api/telegram/linked`.
Людину бот знаходить за робочою поштою (`Employees[Email]` у Power BI). Захист — заголовок `X-Api-Key` =
`TELEGRAM_BOT_KEY` (App Service) = `PAYREQ_TELEGRAM_KEY` (Heroku); без ключа Telegram вимкнено. Черга — таблиця
`telegram_outbox`. «Лише Telegram», а людини немає в боті / заблокувала бота — запасний лист.
За замовчуванням у всіх «Пошта і Telegram». У картці користувача (розділ «Telegram») видно, чи знайшов бот людину
(автоматично за робочою поштою), і адмін може вказати пошту для бота вручну (`user_prefs.telegram_email`).

## Журнал сповіщень
`notify_log.py`, таблиця `notification_log`; сторінка «Адміністрування → Email-сповіщення → 📜 Журнал сповіщень»
(`/admin/notifications`). Кожен лист і повідомлення Telegram (у черзі → надіслано / немає в боті / помилка), а також
«не надсилалось» — кому система могла б надіслати й чому ні: власна дія, вимкнена подія, порожня група ролі,
вимкнена розсилка. Фільтри: канал, результат, пошта або № заявки. У «Деталях» для кожного запису — чому людина
отримала (або не отримала) сповіщення: «ви — фіндиректор», «ви автор цієї заявки», «заявка чекала вашого рішення»…

## Захист форм (CSRF)
Кожна POST-форма містить прихований `csrf_token` (`<input type="hidden" name="csrf_token" value="{{ csrf_token() }}">`
одразу після `<form method="post">`), fetch-запити — заголовок `X-CSRFToken` з `<meta name="csrf-token">` у `base.html`
(Flask-WTF `CSRFProtect`). Без дійсного токена дія не виконується: користувач повертається на сторінку з
поясненням «Сторінка застаріла…» (fetch — JSON 400). Токен діє весь сеанс входу. Виняток — API Telegram-бота
(`/api/telegram/*`, захищено ключем `X-Api-Key`). Cookie сеансу: `Secure` (на HTTPS), `HttpOnly`, `SameSite=Lax`.
Тест `csrf_test.py` перевіряє, що в кожній POST-формі шаблонів є токен.

## Заголовки безпеки й ліміти API
`web/security_headers.py` — на кожній відповіді: `Content-Security-Policy` лише зі своєю адресою (скрипти, стилі,
картинки, шрифти, запити; `object-src 'none'`, `form-action 'self'`, `frame-ancestors 'none'`), `X-Frame-Options: DENY`,
`X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `Permissions-Policy` (без камери, мікрофона,
геолокації), через HTTPS — `Strict-Transport-Security` на рік. Сайт нічого не підключає з інших адрес, тож новий
зовнішній скрипт, шрифт чи картинку браузер заблокує — додайте адресу в `CSP`. Вбудовані `<script>` і `style=` поки
дозволені (`'unsafe-inline'`); щоб CSP захищав і від вставленого скрипта, їх треба перенести в `static/`.

`ratelimit.py` — ліміти для API обробки 1С і Telegram-бота (у пам'яті процесу, за IP): до 600 запитів за хвилину;
після 20 спроб з невірним ключем за 10 хвилин — 429 і для правильного ключа, доки вікно не мине. Тест —
`security_test.py`.

## Секрети
- Секрети (`CLIENT_SECRET`, `FLASK_SECRET_KEY`, publish profile) — **лише** в App Service → Environment variables,
  у секретах GitHub і в локальному `.env`. У коді немає значень за замовчуванням для секретів.
- `.env`, `*.PublishSettings`, `data/`, `*.csv` — у `.gitignore`. Скрипти з паролями в репозиторій не додаються.
- Паролі користувачів системі не потрібні: вхід — через Google / Microsoft, доступ до Power BI — через реєстрацію додатку.
- Якщо секрет потрапив у коміт, чат чи пошту — одразу замініть його (App registration → Certificates & secrets →
  New client secret, оновити `CLIENT_SECRET` в App Service і `.env`, видалити старий). Видалення з історії git
  не допомагає, якщо репозиторій уже був публічним.

## Email-сповіщення
Листи надсилаються через **SMTP** будь-якої пошти (Gmail / Google Workspace, Microsoft 365, SendPulse…).
Усе налаштовується в «Адмініструванні → Email-сповіщення»: сервер, порт, шифрування, логін, пароль додатку,
відправник; там же тестовий лист і журнал останніх листів. Пароль зберігається **зашифрованим**
(ключ виводиться з `FLASK_SECRET_KEY`; якщо його змінити — пароль треба ввести заново) і ніколи не показується.

Gmail / Google Workspace: smtp.gmail.com, 587, STARTTLS; на акаунті відправника — двоетапна перевірка
і «пароль додатку» (myaccount.google.com → Безпека → Паролі додатків).

Користувачі вибирають події в меню «✉ Сповіщення на пошту» (`data/user_prefs.json`, на Azure — `/home/data/`).
Кому з погоджувачів надсилати — з ролей у системі (у кого вказана пошта; людям, колись перенесеним з Azure
лише за ID, пошту бере з довідника `user_directory` або її вводить адміністратор у картці).

**Інша пошта.** Якщо адмін увімкнув «Дозволити користувачам вказувати іншу пошту», користувач може в
«Сповіщеннях на пошту» вказати будь-яку адресу. Вона **замінює** робочу лише після переходу за посиланням
з листа підтвердження (діє 48 год, потрібен вхід тим самим обліковим записом); до того листи йдуть на робочу.
Якщо параметр вимкнути — листи знову йдуть на робочу пошту, збережені адреси лишаються.

`APP_BASE_URL` (необов'язково) — адреса сайту для посилань у листах.

## Дані з 1С (через Power BI)
**Підключено:** `Expense_Item` (статті витрат), `Organizations` (організації: Code, Name, EDRPOU, Country,
CountryGUID, IsDeleted; ключ — Code; резидент — лише країна Україна, порожня чи інша країна — нерезидент) і
`Departments` (відділи: DepartmentCode, DepartmentName, DepartmentGUID, Profitcenter; старі Код_відділу /
Назва_відділу теж читаються), `Employees` (співробітники: EmployeeGUID, Code, Name, Email, IsDeleted, DepartmentGUID,
DepartmentHead; `employees.py`, змінна `PBI_EMPLOYEES_TABLE`) і `Counterparties` (контрагенти: GUID, Code,
Name, FullName, Edrpou, IsNonResident, IsDeleted; ключ — GUID; DirectQuery). Контрагентів десятки тисяч, тому пошук
іде на сервері (`/counterparties/search`), кеш оновлюється раз на 15 хв (`PBI_COUNTERPARTIES_MINUTES`). Новий
контрагент, ще не заведений у 1С, перевіряється наживо за ЄДРПОУ (DAX-запит) кнопкою «Перевірити в 1С зараз» і
автоматично перед «Оплачено». Новий контрагент: назва обов'язкова; для резидента — ЄДРПОУ 8 цифр (юрособи) або
10 цифр (ІПН ФОП / фізосіб) з перевіркою контрольної цифри (код, що вже є в 1С, пропонується як наявний);
для нерезидента номер необов'язковий. Той самий датасет (`PBI_GROUP_ID`,
`PBI_DATASET_ID`); назви таблиць можна змінити змінними `PBI_ORGANIZATIONS_TABLE`, `PBI_DEPARTMENTS_TABLE`.
Кеш — у пам'яті й файлах `pbi_*.json` (`/home/data/`), оновлення — раз на `PBI_CACHE_MINUTES` у фоні або
кнопкою «⟳ Оновити зараз» в адмінці. Помічені на видалення не пропонуються для вибору, але старі заявки їх показують.
«Вид оплати» обов'язковий, лише якщо для організації заявки в довіднику є рахунки / каси.

Довідники приходять з 1С через таблиці датасету Power BI (той самий сервісний принципал і `executeQueries`, що й
для статей витрат). Поки таблиці не підключені — мокові дані у тому ж форматі. Для кожної таблиці: ключ —
GUID посилання 1С, позначка видалення, дата зміни (якщо є), лише елементи (без груп).

**Організація виду оплати.** `PaymentTypes[OrganizationsGUID]` → `Organizations[GUID]`: у «До оплати» колонка
«Платимо з», фільтр і блок «За організаціями» (бачать бухгалтери, фіндиректор, адмін; ініціатори — ні). Без виду оплати —
організація заявки; порожнє посилання 1С (нулі) — «—».

**Валюти.** `Currencies` (GUID, Code — цифровий 980, Name — буквений код UAH, FullName, IsDeleted), `currencies.py`.
У заявці й рядках рахунків — буквений код; позначені на видалення не вибираються (стара валюта заявки лишається).
UAH, USD, EUR — першими в списках і підсумках. Без Power BI — UAH, USD, EUR.

**Види оплати.** `PaymentTypes` (GUID, Code, Name, IsDeleted) і `UserPaymentTypes` (UserGUID, UserName,
PaymentTypeGUID, IsDeleted, EmployeeGUID — вкладка «Виды оплаты» картки користувача 1С). У полі «Вид оплати» бухгалтер
бачить лише свої види оплати з 1С, фіндиректор — усі. Користувача системи зв'язують з користувачем 1С у картці
(«5. Користувач 1С», лише для ролей бухгалтера): точно — через співробітника (пошта → `Employees` → EmployeeGUID),
інакше система підказує найсхожішого за іменем; файл `data/user_onec.json`. Без зв'язку або без видів оплати поле
необов'язкове.

**Новий контрагент, якого ще немає в 1С.** Ініціатор вносить його у вікні вибору контрагента («+ Новий
контрагент»: ЄДРПОУ / реєстр. номер, назва, коментар; перевірка дублів за ЄДРПОУ). Бухгалтер заводить його в 1С
і прив'язує в картці заявки (або система прив'язує сама за ЄДРПОУ під час оновлення довідників). Параметр
«Контрагент, якого ще немає в 1С» в «Оплата й готівка» (`pending_cp_payment`) — коли він уже має бути в 1С: до
погодження бухгалтером, до переходу в «До оплати», до «Оплачено» (за замовчуванням) або не вимагати (з попередженням).
Звірка з платежами 1С закриває лише заявки з контрагентом з 1С, тож для автоматичного «Оплачено» — один із перших двох. Тимчасові контрагенти — `data/counterparties_pending.json` (на Azure — `/home/data/`).

**Вид оплати** — рахунок (безготівка) або каса (готівка) організації, з якої платимо. Бачать і змінюють лише
бухгалтери й фіндиректор; обов'язковий для погодження бухгалтером і для оплати; ініціатор поля не бачить
(ні в картці, ні в історії, ні в листах).
