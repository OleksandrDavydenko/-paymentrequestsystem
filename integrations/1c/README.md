# Обробка 1С «Платіжки із заявок PayDesk»

Зовнішня обробка для 1С:Підприємства 8.3 (керовані форми). Бухгалтер відкриває її в 1С, бачить заявки PayDesk
«До оплати», позначає потрібні й натискає **«Створити платіжки»**. Обробка:

1. створює в 1С **чернетки** платіжних доручень (документ записується, не проводиться);
2. пише в призначення платежу `#номер` заявки — потім звірка з платежами 1С сама закриває заявку в PayDesk;
3. повідомляє PayDesk номер і GUID документа. У картці заявки з'являється «Платіжку створено в 1С № …».

Якщо створити документ не вдалося, обробка повідомляє PayDesk текст помилки. Бухгалтер бачить його і в 1С, і в
картці заявки.

PayDesk у 1С нічого не пише: обробка сама звертається до PayDesk по HTTPS, тож 1С не треба відкривати назовні.

Це **кістяк**: зв'язок, список заявок, створення документа, відмітки в PayDesk і захист від дублів уже є. Які
реквізити документа чим заповнювати, налаштовується таблицею на вкладці «Налаштування», без програміста. Що
доробити під конфігурацію — у розділі [«Що доробити в обробці»](#що-доробити-в-обробці).

## Файли

| Файл | Що це |
|---|---|
| `src/PayDeskPayments.xml`, `src/PayDeskPayments/…` | вихідні файли обробки у форматі вивантаження конфігуратора |
| `src/PayDeskPayments/Ext/ObjectModule.bsl` | уся логіка: HTTP, JSON, пошук у довідниках, створення документа |
| `src/PayDeskPayments/Forms/Форма/Ext/Form/Module.bsl` | форма: команди, список, налаштування |
| `make_xml.py` | генерує XML форми й опису обробки (модулі `.bsl` не чіпає) |
| `build.bat` | збирає `PayDeskPayments.epf` з `src/` |

## Як зібрати `.epf`

Потрібна 1С:Підприємство 8.3 з ліцензією. На комп'ютері, де стоїть PayDesk, ліцензії немає, тож `.epf` там не збирався
й не перевірявся.

```bat
build.bat
```

- Скрипт знаходить `1cv8.exe` у `Program Files\1cv8\8.3.*` і запускає конфігуратор у пакетному режимі з командою
  `/LoadExternalDataProcessorOrReportFromFiles`.
- База потрібна лише для запуску й **не змінюється**. За замовчуванням — `C:\Users\od\Documents\InfoBase1`, іншу можна
  передати параметром: `build.bat "D:\Bases\Test"`.
- Результат — `PayDeskPayments.epf` поруч зі скриптом. Якщо 1С не прийняла файли, текст помилки буде в `build.log`.

Те саме вручну: конфігуратор → «Файл → Завантажити зовнішню обробку, звіт з файлів…» → вибрати `src/PayDeskPayments.xml`
→ «Файл → Зберегти як…» `.epf`.

## Перший запуск

1. **PayDesk.** «Налаштування → API для 1С»:
   - «Створити ключ» — ключ показується **один раз**, скопіюйте його;
   - увімкніть «API для 1С увімкнено».
2. **1С.** Відкрийте спершу копію бази для тестів: «Файл → Відкрити» → `PayDeskPayments.epf`.
3. **Вкладка «Налаштування»:**
   - адреса PayDesk, напр. `https://paymentrequestsystem-ece9b4b4g0dbe7fu.polandcentral-01.azurewebsites.net`;
   - ключ API;
   - вид документа. Обробка сама підставляє перший наявний із `ПлатежноеПоручениеИсходящее`, `ПлатежноеПоручение`,
     `СписаниеСРасчетногоСчета`, `СписаниеБезналичныхДенежныхСредств`, `РасходДенежныхСредств`. Кнопка «Документи
     конфігурації» показує схожі документи й реквізити вибраного.
4. **«Перевірити зв'язок».** Покаже, скільки нових заявок і чи знайшовся в 1С контрагент першої заявки за GUID.
5. **Вкладка «Заявки до оплати»:** «Оновити» → позначити заявки → «Створити платіжки».

Тестовий режим PayDesk («Налаштування → Дані й система») віддає демо-заявки. Так обробку зручно перевіряти на копії
бази 1С, не чіпаючи справжніх заявок. Демо-заявки посилаються на демо-контрагентів, яких у 1С немає, тож довідники
знаходитимуться лише запасним пошуком, наприклад за ЄДРПОУ.

Налаштування (адреса, ключ, вид документа, правила) зберігаються окремо для кожного користувача 1С
(`ХранилищеОбщихНастроек`, ключ `PayDeskPayments`).

**Звідки йдуть запити.** HTTP-запити йдуть із **сервера 1С** (процедури `&НаСервере`). Сервер 1С має мати доступ в
інтернет на порт 443. Якщо доступу немає, перенесіть виклики `ЗапросPayDesk` на клієнт або налаштуйте проксі в
`Новый HTTPСоединение`.

## Правила заповнення («Як заповнити платіжку»)

Кожен рядок задає: **реквізит документа** ← **звідки** взяти значення із заявки. Для довідників спершу шукається
елемент за GUID з PayDesk, а якщо не знайшовся — за реквізитом. Реквізити, яких у документі немає, пропускаються.

| Реквізит | Звідки | Довідник | Шукати за | Поле PayDesk |
|---|---|---|---|---|
| Дата | today | | | |
| Организация | organization | Организации | КодПоЕДРПОУ | edrpou |
| Контрагент | counterparty | Контрагенты | КодПоЕДРПОУ | edrpou |
| СуммаДокумента | amount | | | |
| ВалютаДокумента | currency | Валюты | Наименование | name |
| НазначениеПлатежа | purpose | | | |
| Комментарий | comment | | | |
| Подразделение | department | Подразделения | Наименование | name |

«Звідки»:
- дати: `today`, `pay_date`;
- довідники: `organization`, `counterparty`, `currency`, `department`, `payment_type`, `expense_item`;
- значення: `amount`, `purpose`, `comment` («PayDesk #15 · посилання на заявку»), `note`.

«Шукати за» — `Код`, `Наименование` або ім'я реквізиту довідника. «Поле PayDesk» — `edrpou`, `code` або `name`.

**Захист від дублів.** Перед створенням обробка шукає документ цього виду з коментарем `PayDesk #номер …`, не
позначений на видалення. Якщо його знайдено (документ створено, а відмітка до PayDesk не дійшла), новий не
створюється — у PayDesk відправляється номер наявного. Тому реквізит «Комментарий» варто лишити в правилах.

## Що доробити в обробці

Під конфігурацію Expeditor (у `ЗаполнитьДокумент`, позначка `ПІДЛАШТУВАТИ ПІД КОНФІГУРАЦІЮ`):

- **Рахунок організації** — з «Виду оплати» заявки (`payment_type.ref` — GUID виду оплати з 1С).
- **Рахунок і договір контрагента:**
  - рахунок — основний рахунок контрагента;
  - договір — з рахунку підрядника (`invoices[].deal`) або основний договір.
- **Стаття руху коштів / стаття витрат** — `expense_item.code`.
- **ПДВ і таблична частина** розшифровки платежу, якщо документ її має.
- **Вид операції** — «Оплата постачальнику».
- **Відповідальний** — поточний користувач.
- За бажанням:
  - каса (`form=cash`): видатковий касовий ордер;
  - регламентне завдання, яке створює платіжки без бухгалтера;
  - позначка на видалення документів зі станом `cancelled`.

## API PayDesk для 1С

Усі запити — HTTPS, заголовок `X-Api-Key: <ключ>`, відповіді — JSON (UTF-8).

**Помилки.** Відповідь `{"ok": false, "error": "текст для людини"}` з кодом:

| Код | Коли |
|---|---|
| 403 | API вимкнено, невірний ключ або IP не дозволено |
| 404 | немає заявки |
| 409 | конфлікт (заявка не «До оплати», уже є інша платіжка) |
| 400 | неповні дані |

**Ключ.** Створює адміністратор PayDesk. Він показується один раз, у PayDesk зберігається лише SHA-256. Новий ключ
скасовує старий. Можна обмежити доступ IP-адресами («Налаштування → API для 1С»).

| Метод | Шлях | Що робить |
|---|---|---|
| GET | `/api/1c/v1/ping` | `{"ok": true, "app": "PayDesk", "api": 1, "time": "…"}` |
| GET | `/api/1c/v1/payment-orders?state=new&form=bank&organization=…` | `{"ok", "state", "count", "items": [платіжка…]}` |
| GET | `/api/1c/v1/payment-orders/<request_id>` | `{"ok", "item": платіжка}` |
| POST | `/api/1c/v1/payment-orders/<request_id>/created` | 1С створила документ |
| POST | `/api/1c/v1/payment-orders/<request_id>/failed` | 1С не змогла створити документ |
| POST | `/api/1c/v1/payment-orders/<request_id>/reset` | документ у 1С видалено — заявка знову «нова» |

**Параметри списку:**
- `state`:
  - `new` — «До оплати», платіжки ще немає;
  - `failed` — «До оплати», остання спроба з помилкою;
  - `created` — платіжку створено;
  - `cancelled` — платіжку створено, а заявку потім повернули, відхилили чи скасували; документ у 1С варто позначити
    на видалення;
  - `all` — усі «До оплати» плюс `cancelled`.
- `form` — `bank` / `cash`, без параметра — усі.
- `organization` — код, GUID або ref організації.

**Тіло `created`:**

```json
{"doc_ref": "uuid документа 1С", "doc_number": "ПП-000123", "doc_date": "2026-10-27",
 "doc_type": "ПлатежноеПоручениеИсходящее", "user": "ПІБ бухгалтера", "replace": false}
```

Повтор із тим самим `doc_ref` і номером нічого не змінює. Інший документ для заявки з уже створеною платіжкою дасть
409, доки не передано `"replace": true`.

**Тіло `failed`:** `{"message": "текст помилки", "user": "…"}`.

**Тіло `reset`:** `{"reason": "…", "user": "…"}`.

### Платіжка (елемент `items`)

```json
{
  "request_id": 15, "number": "000000015", "marker": "#15",
  "status": "to_pay", "status_name": "До оплати", "payment_form": "bank", "pay_date": "2026-10-12",
  "amount": "6180.00", "currency": "UAH",
  "currency_ref": {"guid": "…", "ref": "…", "code": "980", "name": "UAH"},
  "organization": {"guid": "…", "ref": "…", "code": "1", "name": "ТОВ …", "edrpou": "…"},
  "payment_type": {"guid": "…", "ref": "…", "id": "…", "name": "ПриватБанк, поточний"},
  "counterparty": {"guid": "…", "ref": "…", "id": "…", "name": "ПрАТ «Київстар»", "edrpou": "21673832",
                   "code": "…", "in_1c": true},
  "expense_item": {"code": "02.001", "name": "Зв'язок та інтернет"},
  "department": {"guid": "…", "ref": "…", "code": "LOG", "name": "Логістика"},
  "invoices": [{"number": "НП-104512", "amount": "12450.00", "currency": "UAH", "deal": "Договір №15/2025"}],
  "purpose": "Оплата за рах. № НП-104512; Договір №15/2025, #15",
  "note": "коментар автора", "author": {"name": "…", "email": "…"},
  "approved_at": "2026-10-09T12:15:00", "url": "https://…/requests/15",
  "onec_state": "new", "onec_order": null
}
```

**`guid` і `ref`:**
- `guid` — як у SQL-базі 1С (`_IDRRef`, 32 hex), так ці коди приходять у PayDesk з Power BI;
- `ref` — той самий ідентифікатор у вигляді `УникальныйИдентификатор` 1С. Байти переставлені:
  `ref = h[24:32]-h[20:24]-h[16:20]-h[0:4]-h[4:16]`. Тож `Справочники.X.ПолучитьСсылку(Новый УникальныйИдентификатор(ref))`
  дає той самий елемент.
- Якщо GUID невідомий (тимчасовий контрагент, демо-дані), `guid` і `ref` — `null`.

**Контрагент не з 1С.** `counterparty.in_1c = false` означає, що контрагента ще не заведено в 1С. Обробка таку заявку
не оформлює. Щоб такі заявки не доходили до «До оплати», у PayDesk є налаштування «Контрагент, якого ще немає в 1С:
коли він уже має бути в 1С».

**Призначення платежу** — рахунки й договори з заявки (або стаття витрат), у кінці — `#номер`, до 420 символів.
Номер у призначенні потрібен, щоб звірка PayDesk сама знайшла заявку за платежем.
